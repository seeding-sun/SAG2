# SAG2 评分尺度改造方案：0/1 二值 → 10 分制 + 阈值不填充

日期：2026-11-12
状态：**设计稿，尚未改动任何代码**（等待评审后实施）
基线臂：A1（0/1 二值，`jev_score ∈ [0,1]`）
目标臂：**D1**（10 分制 + 阈值过滤，`grade ∈ {0,2,4,6,8,10}`）

## 0. 前置事实核查（先确认改哪里，否则会改错文件）

动手前核对了 A1 产出的真实来源，有两条容易搞错的事实：

**事实 1：A1 不是 `run_sag2_benchmark.py` 跑出来的，是 `run_hybrid_compare.py`。**

判定依据：

| 证据 | 说明 |
|---|---|
| `qwen_scorer_sha256` 只在 `run_hybrid_compare.py:182` 计算 | `run_sag2_benchmark.py` 里根本没有这个字段 |
| A1 的 `config.json` 含 `evidence_batch_size / evidence_concurrency / response_format / embedding_model / rrf_k / bm25_weight / pool_k` | 全是 `run_hybrid_compare.py` 的参数 |
| trace 里每批恰好 10 个候选 | `--evidence-batch-size` 默认 10 |

**这条很重要**：`run_sag2_benchmark.py` 走的是 `JevClient`（`scripts/sag2.py:756`，`/systemone` + `noul` 协议，**按 64k tokens 打包、没有 batch 上限**），而 A1 走的是 `QwenEvidenceScorer`（`scripts/qwen_evidence_scorer.py`）。**两者是完全不同的打分实现，不能混为一谈。**

所以：

- 本方案改的是 `scripts/qwen_evidence_scorer.py`（D1 复现 A1 的路径）
- `JevClient` 路径本次**不动**（它属于另一条实验线）

**事实 2：当前工作区的 `qwen_evidence_scorer.py` 不是 A1 用的那个版本。**

```
A1 记录 qwen_scorer_sha256 = 8c3d0ba7...
当前工作区文件         sha256 = 9f2bef75...    ← 不一致
git show HEAD 版本            = 8c3d0ba7...    ← 与 A1 一致
git diff --stat              = +50 / -7        ← 未提交的"候选 ID 单字符删除修复"
```

即：**A1 跑的是 HEAD（已提交）版本；工作区多了未提交的 ID 修复**（见《工程记录》§2、§8）。这意味着：

- D1 的 `config.json` 会记录到与 A1 不同的 `qwen_scorer_sha256`，**这属预期**；
- 但在开跑 D1 之前，必须先决定这个未提交修复的归属（提交 / 单独分支），**否则 D1 的可复现性无法保证**——将来无法凭哈希判断 D1 到底用了哪版代码。

## 1. 动机：为什么必须改

诊断发现当前 A1 臂的打分器实际是**二值**的，不是 0~1 连续：

```
全部 20,789 个候选的分数分布
  1.0  →    352 个   ( 1.7%)
  0.5  →      1 个
  0.0  → 20,436 个   (98.3%)
```

由此产生三个连锁后果：

| 后果 | 实测 |
|---|---|
| 每题非零候选极少 | hop0 平均 **1.61** 个，hop1 平均 **1.92** 个（总分池 100 / 110） |
| 种子 84% 靠 0 分填充 | 1000 个 seed 席位中，161 个有分、**839 个 0 分**（实测 100/100 题 `protected ⊆ seeds`） |
| 排序退化到按 id | hop2 那 80 个旧候选席位 **100% 全 0 分**，`(-score, id)` 实际变成**按 id 升序** |
| DPP 失效 | 最终 top-10 里有 **17/100 题全 0 分** → kernel 退化成全零矩阵 |

根因不只是刻度粗，而是**判定标准是个是非题**：

```python
CRITERION = "Is this candidate itself necessary evidence in a fully supported answer chain ..."
```

配合 `"Use no outside knowledge."`，模型几乎无法确认"必要"，于是答 no → 0。

**只把 0~1 改成 0~10 而不改判定标准，模型大概率仍只出 0 和 10。** 所以刻度与判定标准必须一起改。

## 2. 决策记录

| 决策点 | 选定 | 说明 |
|---|---|---|
| 改造范围 | **B：改刻度 + 改判定标准为分级 rubric** | 只改刻度无效 |
| 阈值语义 | **读法 A：重定义分档，使 4 = "上链但不完整"** | 让用户直觉的"4"成为有意义的边界 |
| 4 分以下 | **不保留、不填充** | 种子数可少于 10，也可为 0 |
| 阈值作用范围 | 种子选择 + hop2 旧候选准入 | **不作用于最终交付**（见 §5） |
| hop2 那 80 席 | **同样套用阈值** | 否则 hop2 仍按 id 挑 80 个 |
| 其它变量 | 保持不动 | `seen` 排他机制本次不改（见 §8） |

### 2.1 支持"不填充"的实测依据

用 A1 臂 100 题真实分数重放（种子用 hop0 分数，最终排序用 hop1 分数，与代码一致）：

| 方案 | Recall@10 |
|---|---|
| 现状：取前 10，不足用 0 分填充 | 0.5825 |
| **不填充：只保留 ≥4 分种子** | **0.5933（+0.0108）** |

原因是填充种子**不是中性的，而是有害的**：有 17/100 题一个 ≥4 分的种子都没有，填充的 0 分候选抽出的词把扩展引向了错误方向，这些题的扩展结果比"不扩展"更差。

**该模拟的可信度**：重放"现状"得到的 Recall@10 = **0.5825**，与 A1 记录值**逐位相同**；说明重放逻辑（种子取 hop0 分数、最终排序取 hop1 分数、`(-jev, -fusion, id)`）与真实管线一致，因此 "+0.0108" 的差值可信。

## 3. 分级 rubric（读法 A）

### 3.1 分档定义

| grade | 含义 | 是否上链 |
|---|---|---|
| 0 | 主题无关，或指向错误实体 | 否 |
| 2 | 主题相关，但不含任何可用事实（仅关键词重合） | 否 |
| **4** | **提供答案链上的一个事实，但需其他片段配合才能定位或成立** | **是（弱）** |
| 6 | 提供答案链的中间事实，可独立确立一步 | 是 |
| 8 | 提供关键事实，但实体或关系存在歧义 | 是 |
| 10 | 直接且完整地支撑答案链的一环 | 是 |

**边界即阈值**：`grade >= 4` ⇔ "上链"。4 分以下一律不要、不填充。

保留 6 档（而非 11 档）的理由：档位越少，模型越稳定；相邻档的语义差距足够大，便于人工审计。内部仍可解释为"0~10 连续刻度上的 6 个锚点"。

### 3.2 提示词要求（三条，缺一不可）

1. **改成评级指令**，不再是是非问句：`rate how much this passage contributes to a supported answer chain`。
2. **给出全部锚点**，并说明"必须使用中间档"。
3. **明示 0 分的严格性**：只有确实完全无关或指向错误实体才给 0；不得因"不确定"给 0。

### 3.3 防止塌成两极的补充手段

即使有锚点，模型仍可能保守塌成两极。备选强化（**建议 D1 先按 §3.1/3.2 实施，若验收不达标再启用**）：

- 批内相对化：要求"本批最好的给 10"，强制拉开分布。缺点：依赖单批，且引入批内偏置。
- 两段式：先三分类（必要/相关/无关），再只对前两类打 0~10。成本略高，但注意力集中。

## 4. 两层分离：不让 0~10 扩散到全链路

这是本方案风险控制的核心。**只在打分器内部用 0~10，对外接口仍是 `[0,1]`。**

```
第 1 层（模型输出）: grade ∈ {0,2,4,6,8,10}   ← 字段名 grades，新增
第 2 层（内部存储）: jev_score = grade / 10    ← 仍 ∈ [0,1]
第 3 层（trace）  : 额外记录 grade 原值        ← 便于按档位审计
```

好处：**下游零改动**。

| 下游组件 | 是否受影响 | 原因 |
|---|---|---|
| `ranked()` 排序 `(-jev, -fusion, id)` | 否 | 单调正变换不变 |
| 扩展词权重 `0.5 + 0.5*(score/max_score)` | 否 | 归一化后不变（但分数拉开后区分度更好） |
| DPP kernel `score_i * score_j` | 否 | 正比例缩放不变 |
| `parse_scores`（校验 `0 <= v <= 1`） | **否，保持原样** | 新增独立的 `parse_grades` |
| 报告脚本 / 指标 | 否 | 仍读 `jev_score` |
| `local` 模式的 true/false jev 路径 | **否** | 见 §6.2 的常量隔离 |

## 5. 阈值的三个作用范围

### 5.1 种子选择（套用）

```python
frontier = [
    c for c in ranked() if c["id"] not in expanded and c["jev_score"] >= threshold
][:seed_k]
```

- 种子数**允许少于 10**，也**允许为 0**。
- 为 0 时，现有逻辑 `if hop and not frontier: break` 已正确表达"无种子则不扩展"，**无需改**，但必须记录 trace 便于分组统计。

### 5.2 hop2 旧候选准入（套用）

```python
previous = sorted(
    (c for c in latest.values() if c["jev_score"] >= threshold),
    key=lambda c: (-c["jev_score"], -c["fusion_score"], c["id"]),
)
```

同时修正一个现存不一致：原代码 `key=lambda c: (-c["jev_score"], c["id"])` 缺 `-fusion_score`，与 `ranked()` 不一致。在 98.3% 全 0 分的现状下，这一行决定 hop2 那 80 席按 id 排序。

**代价预警**：hop2 池子会从 120 显著缩小（`种子 + 有分旧候选 + 20 新`）。若缩小过度，需在 trace 里记录池大小分布，验收时检查中位数是否低于可接受下限。

### 5.3 最终交付（**不套用**）

```python
final = ranked()[:candidate_k]        # 保持原样，交付满 10 篇
final = rank_dpp(final[:10], index.diversity_idf) + final[10:]
```

原因（实测）：

| | Recall@10 | 平均交付篇数 |
|---|---|---|
| 阈值只作用于种子/hop2 | 0.5825 | 10.0 |
| 阈值**也**作用于交付 | 0.4650（−20%） | **1.92** |

交付层一过滤就只剩 1~2 篇，`Recall@10` 与 `AllEvidence@10` 会崩。

**替代方案**：交付仍满 10 篇，但额外报告诊断指标 `有效交付@10`（= 前 10 篇中 grade≥4 的篇数），用于衡量"交付质量"而不牺牲指标口径。

| 位置 | 动作 |

### 6.2 改动 2：新增 rubric 常量（`scripts/sag2.py`）

**关键：不要改 `CRITERION`。**

`CRITERION`（:100）被两处使用：

| 使用方 | 位置 |
|---|---|
| `JevClient`（`/systemone` 协议） | `sag2.py:856` |
| `QwenEvidenceScorer` | `qwen_evidence_scorer.py:16` 导入，用于 `CRITERION` 字段 |

改它会**同时**改变 `JevClient` 实验线的契约（那条线还配着 true/false `criteria`，见 `:860-863`）。因此：

```python
GRADE_CRITERION = "Rate how much this passage contributes ..."   # 新增
GRADE_RUBRIC = {0: "...", 2: "...", 4: "...", 6: "...", 8: "...", 10: "..."}  # 新增
```

`JevClient` 与 `local` 模式继续用 `CRITERION` + true/false，行为完全不变。

### 6.3 改动 3：阈值过滤（`scripts/sag2.py`）

| 位置 | 动作 |
|---|---|
| `search_sag2` 签名 | 新增 `grade_threshold: float = 0.0` |
| `:1067` `frontier` | 加 `and c["jev_score"] >= grade_threshold` |
| `:1037` `previous` | 加过滤 + 补 `-fusion_score` |

### 6.4 改动 4：批次大小（走命令行参数，不改代码）

`--evidence-batch-size` 从 **10 → 100**（`run_hybrid_compare.py:92`）。

理由：10 分制下，`batch_size=10` 意味着 100 个候选拆成 10 个独立请求，**跨批分数不可比**，而种子是从 10 批混在一起排出来的。

体量实测：

```
平均 484 字符/片段 ≈ 138 tokens
100 篇 ≈ 14k tokens；最坏 100 × 574 ≈ 57k
hop2 池 120 篇最坏 ≈ 69k → 自然拆成 2 批
服务上限 max_request_tokens = 64k
```

因此**不新增逻辑**，只需把该参数调大，现有 `_pack_candidates`（`:184`）的 token 守卫会自动在必要时切分。附带收益：`state`（约 3k tokens）不再被 10 个批次各重复一次。

> 注：本项仅作用于 `run_hybrid_compare.py` / `QwenEvidenceScorer` 路径。`JevClient` 本就按 64k 打包、无 batch 上限，不受影响。

## 8. 本方案不解决的问题（务必区分）

| 问题 | 本方案能否解决 | 原因 |
|---|---|---|
| 种子 84% 靠 0 分填充 | **能** | 阈值直接砍掉 |
| 最终 top-10 有 17 题全 0 分、DPP 失效 | **能** | 分数拉开后 kernel 有效 |
| hop2 那 80 席按 id 排序 | **能** | 阈值 + 补 `fusion_score` |
| hop0 的 34 个 gold 掉出池子、扩展 0 次捞回 | **不能** | 是 `seen` 排他（`rowid NOT IN (SELECT value FROM json_each(?))`） |
| 扩展新候选 gold 命中率仅 0.49% | **基本不能** | 是 BM25 词面匹配问题 |

**收益上限**：种子精度 15.8% → 理论天花板 **29.0%**（290 gold / 1000 席位）。天花板由"池内有多少 gold"决定，不是打分器能突破的。

因此 D1 即便完全成功，H=1 的 AE@10 也可能仍在误差内持平——**必须分组看**（见 §9）才能看出真实作用。

## 9. 验收方案（20 题小样本，先花小钱）

### 9.1 规模与成本

20 题 × {H=0, H=1}；单批后请求数约为 `20 × 2 × 1 ≈ 40`（旧方案为 `× 10`）。

### 9.2 通过标准

| 指标 | A1 基线 | D1 通过线 |
|---|---|---|
| 实际使用档位数 | 2（0/1） | **≥ 5** |
| 每题有分（≥4）种子数 | 1.61 | **≥ 5** |
| 无种子题比例 | 17% | **≤ 5%** |
| 种子精度 | 15.8% | **≥ 22%** |
| 同批重测一致性（跑两遍） | — | Spearman **≥ 0.8** |
| `batch=10` vs 单批 排序一致性 | — | Kendall τ **≥ 0.8** |

### 9.3 必须分组报告（否则会看错）

```
组 A：有种子题（grade≥4 至少 1 个）
组 B：无种子题（退化为 H=0）

两组分别报 Recall@10 / AllEvidence@10 / 平均有效交付@10
```

若不分组，20% 的题"扩展根本没发生"会与"扩展有效"混在一起，均值看不出真实收益。

### 9.4 验收脚本（待实施）

新增 `scripts/diagnostics/diagnose_grades.py`：

1. 读 `details.jsonl`，统计 `jev_grade` 直方图（验证档位数，不是 2）。
2. 统计每题 ≥4 分候选数分布、无种子题比例。
3. 重算种子精度，与 A1 对比。
4. 分组（有种子/无种子）重算指标。
5. **自校验**：用 trace 重放排序，须与 `retrieved_source_ids` 100% 一致（沿用 `diagnose_ranking.py` 的做法）。

## 12. 20 题小样本验收结果

样本：`dataset/musique_20_for_grades.json`，按父样本 8/6/6 分层（2hop/3hop/4hop），取自 A1 同源 100 题、保持 A1 运行顺序，因此可与 A1 逐题配对。

### 12.1 结构与精度指标

| 指标 | A1（0/1） | D1 `batch=10` | D1 `batch=100` | 通过线 |
|---|---|---|---|---|
| 实际使用档位数 | 2 | **6** | **6** | ≥5 ✅ |
| 每题种子数（均值） | 10.00（全填满） | **6.95** | **3.50** | ≥5 ⚠见下 |
| 填充席位（<阈值） | 90/200 | **0/139** | **0/70** | 0 ✅ |
| 无种子题比例 | 0% | **0%** | **0%** | ≤5% ✅ |
| 种子精度 | 16.50% | **23.74%** | **50.00%** | ≥22% ✅ |
| Recall@10（20 题） | 0.6542 | 0.6875 | **0.7583** | — |

**"不填充"被彻底验证**：A1 的 200 个种子席位里有 90 个是 0 分填充；D1 两个配置的填充席位都是 **0**，不足 10 个就少给，符合"4 分以下不要、也不填充"。

### 12.2 关键发现：批次大小会改变绝对分数校准

| | 每题种子数 | 种子精度 | Recall@10 |
|---|---|---|---|
| `batch=10`（10 批） | 6.95 | 23.74% | 0.6875 |
| `batch=100`（1–2 批） | 3.50 | 50.00% | 0.7583 |

**Kendall τ（hop-0 逐题）**：均值 **0.9835**，最小 0.8404，低于 0.8 的题 **0/20**。

即：**相对排序几乎不变（τ≈0.98），但绝对分数整体下移**。单批打分更严格，过阈值 0.4 的候选少了近一半，可种子质量翻倍、最终 Recall 更高。

这条对方法学很重要：**阈值 0.4 不是一个跨批次不变的量**。批大小决定"多少候选算上链"，因此换批大小必须重新标定阈值。§9 里"每题 ≥5 个种子"这条通过线在 `batch=100` 下不适用——种子只有 3.50 个，但精度 50%、Recall 更高，说明这条指标本身设计得不对，应改为以**下游 Recall 与种子精度**为准。

### 12.3 必须如实说明：Recall 提升在 20 题上不显著

逐题配对（vs A1）：

| arm | Recall@10 | 提升题 | 下降题 | 持平 |
|---|---|---|---|---|
| b10 | 0.6875 | 5 | 3 | 12 |
| b100 | 0.7583 | 5 | 2 | 13 |

`b100` 相对 A1：提升 5 题、下降 2 题，**单侧符号检验 p = 0.227（n=7）**。

所以：

- **结构性指标（档位数、填充归零、种子精度）是确定性测量，可信**；
- **Recall@10 的 +10.4pt 只是方向性证据，20 题不足以判定显著**，必须上 100 题才能定论。

### 12.4 自校验

`diagnose_grades.py` 用 trace 重放排序，并与 `retrieved_docs` 映射回 document id 的集合比对（`rank_dpp` 只重排 `candidate_k` 前缀，故集合必须完全一致）：

```
D1-b10 : 20/20
D1-b100: 20/20
A1-20  : 20/20
```

三个 run 全部通过，说明本节所有重算指标（含种子精度、分组 Recall）建立在正确的重放逻辑上。

### 12.5 结论与下一步

- 5 项验收标准中，**4 项决定性通过**（档位数、填充归零、无种子比例、种子精度）；"每题 ≥5 种子"这条在 `batch=100` 下不达标，但判定为**指标设计问题**而非缺陷。
- 建议 **D1 采用 `batch=100`**（精度 50%、Recall 更高、请求数少 10 倍），但需在 100 题上重新标定阈值（可考虑 0.3）。
- 下一步：跑 100 题 `D1-H0` / `D1-H1`，与 A1 做配对比较；`batch=10` 保留为消融。
