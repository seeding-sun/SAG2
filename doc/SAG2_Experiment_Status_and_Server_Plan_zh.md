## 0.3 服务状态与模型切换决定（2026-11-13）

### 0.3.1 事实：网关会静默换模型

证据判定网关**不按请求的 `model` 字段路由**，不可达的大模型被静默映射到小模型：

| 请求 | 实际返回 |
|---|---|
| `qwen3.5-122b-a10b` | **`qwen3.8-27b`** ❌ |
| `qwen3.5-397b-a17b` | `qwen3.6-27b` ❌ |
| `qwen3-235b-a22b` / `qwen3-30b-a3b` / `qwen2.5:32b` | `qwen2:7b` ❌ |
| `qwen3.6-27b` / `qwen3.8-27b` / `gemma4-26b-a4b` | 原名返回 ✅ |

`/v1/models` 仍**列出** `qwen3.5-122b-a10b`，但请求它返回 27B——清单是静态的，实际路由取决于后端在线实例。

`D1-H1` 因此被污染：`2026-11-13 10:54:04` 起，最后 **14 题（全 4hop）** 由 27B 判定，涉及 260/2,094 批次。**结论未被推翻且更强**：干净 86 题上 R@10 差值 +0.1192（Holm p=0.002），符号检验 29 胜 / 6 负。详见 `SAG2_D1_Grade_Scale_100Q_Report_zh.md` §3.7 与工程记录 §19。

### 0.3.2 决定：改用 27B，并重跑匹配基线

运维反馈 122B 实例"有时候会出问题"。既然网关可能随时把 122B 换掉，**继续把 122B 当基准臂是不可靠的**。决定：

> **后续实验统一使用 `qwen3.8-27b`。**

**但这带来一个必须处理的科学问题：换模型会切断与已跑完两组结果的可比性。**

`A1-H1` 与 `D1-H1`（86 题干净部分）都是 122B 判定的。直接用 `D1+B1@27B` 去比 `A1-H1@122B`，差值里混着"检索方式改动"和"判定模型改动"两个因素，结论无效。

**因此 27B 实验必须自带匹配基线：**

| 臂 | 检索 | 判定 | 作用 |
|---|---|---|---|
| `A2-H1-qwen3.8-27b` | BM25 | 二值 | 27B 基线（等价于 A1-H1，但换模型） |
| `A6-H1-qwen3.8-27b` | BM25 | 6 档 + 不填充 | 检验 **D1 效应能否跨模型迁移** |
| `D1+B2-H1-qwen3.8-27b` | hybrid | 6 档 + 不填充 | 目标臂 |

只有 `A2-H1-qwen3.8-27b` vs `A6-H1-qwen3.8-27b` 这一对能回答"分级评分在 27B 上是否同样有效"；`A6-H1-qwen3.8-27b` vs `D1+B2-H1-qwen3.8-27b` 才能干净地回答"换检索方式带来多少"。

### 0.3.3 为什么重跑基线是划算的

27B 比 122B 快约 **8.5 倍**（同规模真实请求：1.34 s vs 11.4 s 单批）。100 题单臂墙钟从 1 小时 51 分降到约 40 分钟量级，所以重跑两个基线臂的成本可以接受。

这也顺带得到一个额外结论：**判定侧换小模型在经济上是可行的**，如果精度损失可控。

### 0.3.4 已知风险：阈值 0.4 可能在 27B 上失准

阈值 0.4（grade ≥ 4）是在 **122B + batch=10** 下标定的。27B 的 14 题样本显示它更保守：

| | 122B（干净 86 题） | 27B（被污染 11 题） |
|---|---:|---:|
| 每题种子均值 | 5.40 | **2.50** |
| 种子精度 | 28.23% | **55.56%** |

27B 给更少但更准的种子。若 `A6-H1-qwen3.8-27b` 出现大量"种子过少"（甚至无种子），说明阈值需要往 0.3 方向重标定，而不是改用更松的 rubric。

**另需注意**：`threshold 0.4` 的正确读法是"grade ≥ 4"，27B 若系统性给低分，等价于提高了门槛。

### 0.3.5 新加的守卫

事故 9 之后新增两道防线：

1. **运行时硬断言**：`qwen_evidence_scorer.py` 新增 `QwenModelMismatch`。默认 `strict_model=True`，返回模型与 `--evidence-model` 不一致即抛错且**不重试**（重试无意义，网关会一直替换）。需要容忍时显式传 `--no-strict-model`，此时把不匹配记入 `model_mismatches`。
2. **事后审计脚本**：`scripts/diagnostics/check_model_consistency.py`，比对 `batches[].model` 与 `config.evidence_model`，污染时退出码 1 并输出干净子集指标。

单元测试从 133 增至 **137**（新增 4 条覆盖：静默替换必须失败、错误信息含双方模型名、非严格模式记录不匹配、响应缺 `model` 字段不应误判）。

#### 0.5.4 对"要不要扩到 10 档"的直接回答

不需要，而且方向错了。

- 27B 的问题不是档位不够细，是**过 4 分的候选太少**（2.85%）。把 6 档拆成 10 档只会让每档更稀疏，不改变过线总量。

- 看起来该动的是**门坎 τ**（按 122B 标定，在 27B 上等价于被抬高）。这一条已在 §0.5.6 实测，**同样不成立**。

#### 0.5.6 阈值重标定实测：假说被证伪

**先纠正一个方法论问题**：档位锚点是 `{0, 2, 4, 6, 8, 10}`，`jev_score = grade / 10`。所以 **τ=0.3 与 τ=0.4 完全等价**（都要求 grade ≥ 4）。能改的只有 τ=0.2（放入 band 2）、τ=0.4、τ=0.6。原先计划的"扫描 τ∈{0.2,0.3,0.4}"里有三分之一是空操作。

于是直接在 **4-hop 全部 30 题**上实测 τ=0.2（`A6-H1-qwen3.8-27b.tau02-4hop`，审计干净）：

| | A2-H1-qwen3.8-27b | A6-H1-qwen3.8-27b（τ=0.4） | A6-H1-qwen3.8-27b（τ=0.2） |
|---|---:|---:|---:|
| R@10 | 0.5167 | **0.5250** | 0.5167 |
| 种子均值 | — | 2.47 | **3.27（+32%）** |
| 种子分布 | — | 0:1, 1:7, 2:8, 3:8, 4:3, 5:3 | 0:1, 1:3, 2:7, 3:8, 4:5, 5:3, 6:1, 8:2 |

**种子成功增加了 32%，R@10 却回落到基线水平，比 τ=0.4 还低 0.83pp。** 逐题对比 1 胜 / 1 负 / 28 平。

**结论：种子断供假说被证伪。** 放低门坎补进来的 band-2 候选按 122B 的档位精度只有 **2.37%**（接近随机），它们污染了扩展查询而不是提供词项。这反过来**强化了"不填充分"的原始设计决定**：宁可扩展不足，也不能用噪声喂扩展。

因此 27B 上 4-hop 的增益塌陷**不是门坎问题，而是 27B 判定器在本任务最难层上的信息量确实更低**。要改善 4-hop，需要动的是**第一轮池内 gold 覆盖**（§4.7 已论证这是最陡的杠杆），而不是评分尺度或检索融合。

| 丢失 | 15 | **10** | −5 |
| 补回 | 39（25.49%） | **64（41.83%）** | **+25** |

**净增 30 个 gold 里，25 个来自"补回"，只有 5 个来自"少丢"。** 保住率本来就接近 90%，不是主要矛盾。

补回的 +25 再拆一层：**+12 是"第一轮 100 池里本来就有，分档让它排上来了"（只需重排），+13 是"扩展把新的捞回来"（需要检索），恰好一半一半。** 前者容易被忽略——扩展轮虽只保留 5 个 BM25 保护项，但第一轮 100 个候选的 `jev_score` 一直留在 `latest` 里参与最终排序。

按跳数的补回率：2hop 39.3%→58.9%，**3hop 22.0%→51.2%（2.3×，主战场）**，4hop 27.5%→34.2%（几乎没改善）。

剩余 110 个未进 top-10 的 gold：**46 个是"池里有但没排进"（纯排序问题），43 个是"扩展没捞到"（纯覆盖问题）**，量级相当。

#### S3.5.6 决策：下一臂跑 `D1+B1`（hybrid + 6 档 + 不填充）

| 检索 | 首轮 R@10 | 池内 gold | 二值下 H0→H1 |
|---|---:|---:|---|
| BM25（A1） | 0.5067 | 1.92 | +0.6 pp |
| **hybrid（B1）** | 0.5800 | **2.24** | +1.8 pp |
| dense（C1） | 0.5950 | 2.32 | **−3.0 pp** ⚠️ |

三个依据：

1. **池内 gold 是最陡的杠杆**：同 D1 数据里，池内 1 个 → 2 个，最终 R@10 从 0.5726 跳到 0.7396（+0.167）。注意分组有混淆，仅作方向性证据。
2. **hybrid 是唯一"首轮更好 + 二值下扩展也为正"的配置**，dense 虽然首轮最高，但二值下扩展轮是负收益。
3. **dense 的 −3.0 pp 是一个可检验的预测**：若"污染假设"成立，D1 去污染后应收敛为正。留作后续机制验证臂。

运行参数：`--concurrency 6`（上一轮 `3` 是为共享实例让路，单题计算量已证明与 A1 相同），预期墙钟约 55 分钟。需先构建 hybrid 所需的 BGE 向量（若缓存仍在，可复用）。

**方向性预期 0.72–0.77，不是承诺值。**

### 阶段 S4：RRF 改进实验

只有确认 C 优于 B 后再做：

```text
等权 RRF
偏 BGE RRF：1:2
偏 BGE RRF：1:3
BGE 配额 + BM25 补召回
```

必须使用独立调参集，避免在最终 100 题上过拟合。

## 5. 服务器运行方式

### 5.1 拉取代码

```bash
git clone https://github.com/seeding-sun/SAG2.git
cd SAG2/SAG-Benchmark/sag2
```

后续更新：

```bash
git pull --ff-only
```

### 5.2 安装依赖

```bash
uv sync --frozen --dev
```

### 5.3 配置环境

```bash
cp .env.example .env
```

在服务器本地编辑 `.env`：

```dotenv
SAG_EMBEDDING_BASE_URL=http://192.168.2.108:8013/v1
SAG_EMBEDDING_MODEL=bge-m3:latest
SAG_EMBEDDING_API_KEY=

SAG_EVIDENCE_BASE_URL=http://192.168.2.69:9099/v1
SAG_EVIDENCE_MODEL=qwen3.5-122b-a10b
SAG_EVIDENCE_API_KEY=服务器本地填写
```

`.env` 已被 Git 忽略，不能提交。

### 5.4 100 题 H=0

从仓库根目录执行：

```bash
cd SAG-Benchmark/sag2
uv run python scripts/run_hybrid_suite.py \
  --dataset-dir ../../dataset \
  --sample-file ../../dataset/musique_100_for_ab.json \
  --output-root ../../output/abc-100/H0 \
  --arms bm25 dense hybrid \
  --max-hops 0 \
  --candidate-k 100 \
  --seed-k 10 \
  --concurrency 4 \
  --evidence-concurrency 1
```

该脚本会：

1. 检查 BM25 索引；
2. 检查 BGE cache；
3. 缺少时自动构建；
4. 依次运行 A、C、B；
5. 使用 `details.jsonl` checkpoint 支持恢复。

三个 H=0 实验臂：约 28.5 分钟 / 10 题

代码、脚本、固定题集、实验方案和汇总报告提交到 GitHub。

comparison-*.json
